# Готовность Okoscope к публичному релизу — 2026-09-03

## Вывод и границы оценки

Okoscope выглядит как функционально развитая alpha, пригодная для пилотов с сопровождением. Публичная beta для узкого, явно поддерживаемого профиля реалистична после закрытия установочных и эксплуатационных пробелов. Оснований объявлять production-ready GA пока недостаточно.

Оценены backend и frontend, включая код, API, deployment, CI, тесты и сохранённые отчёты. Контракты OpenAPI в двух репозиториях совпадают побайтно. Это аудит исходников и имеющихся свидетельств, не новый прогон тестов, pentest, нагрузочная сертификация или проверка текущего production. Оценка стадии — экспертное суждение, не измеренный процент готовности.

Исходное предположение о рынке: self-hosted инструмент для SRE/platform-команд, расследующих изменения runtime-поведения Kubernetes-приложений. Для публичного SaaS требования к изоляции, abuse protection и управлению аккаунтами существенно строже.

## Что уже является продуктом

- Наблюдение процессов, выбранных syscalls, исходящих и входящих соединений, DNS, файловой активности, завершений и рестартов. Возможности имеют отдельные ограничения и настройки включения.
- Organization → Project → Application, scoped API, runtime inventory, группы повторяющегося поведения и acknowledge/resolve/reopen.
- Releases, runtime diff, attention summary, политики с preview/revisions и suppression. Это уже основа законченного расследования изменения поведения.
- Cookie sessions, Argon2, роли owner/member, trusted-Origin проверка изменений, отдельные ingestion credentials, ротация/отзыв и хранение digest.
- Durable webhook delivery с HMAC, retries, leases, recovery, idempotency и health; retention сырых событий и численной истории с явным покрытием данных.
- Frontend имеет onboarding, страницы расследования и настроек; есть TypeScript/OpenAPI, unit/component, Playwright и accessibility-проверки.
- Backend CI включает strict Clippy, userspace tests, часть PostgreSQL tests и валидацию Kubernetes-манифестов. Есть сохранённые acceptance-отчёты реального кластера и локальных benchmark.

Источники: [API](../openapi/okoscope-v1.yaml), [attention](attention-summary.md), [retention](runtime-events-retention.md), [notification acceptance](notification-activation-audit.md), [CI](../.github/workflows/ci.yml). Наличие тестов не означает, что они заново прошли в рамках этого аудита.

## P0: перед самостоятельной публичной beta

### 1. Воспроизводимая установка и обновление

Есть Kustomize и UI подключения агента, но документация содержит фактические расхождения:

- Команда создания Secret в `self-hosted-deployment.md` не создаёт `identity-token-key`, обязательный в `server/resources.yaml` и указанный в `secret.example.yaml`.
- Инструкция ссылается на `01-install-bundled-postgres.yaml` и `03-upgrade.yaml`, которых нет в текущем checkout; одновременно заявляет отказ от генерации release bundles.
- Документация описывает публикацию server amd64/arm64 и продвижение только server; текущий CI публикует amd64 server/agent и продвигает оба.
- Deployment содержит конкретные namespace, workload, image refs и инфраструктурные предположения авторского окружения.

Нужен один документированный install path с параметрами, preflight совместимости/секретов, миграцией, подключением workload и первым событием. Helm удобен, но конкретный упаковщик не обязательнее работающей установки. Критерий: независимый человек ставит с нуля по документации и проходит обновление без устных подсказок автора. Цель 15–30 минут — предлагаемая продуктовая метрика, не текущее измерение.

### 2. Безопасные настройки поставки и защита входа

TLS реализован, однако поставляемая конфигурация агента использует HTTP и `developmentPlaintext: true`, сервер — `OKOSCOPE_DEVELOPMENT_PLAINTEXT: true`. Для рекомендуемого production install нужен проверенный TLS path. По просмотренному коду и deployment не найден rate limiting входа/регистрации. Login синхронно выполняет Argon2 и создаёт dummy hash на каждом запросе: нужны ограничение частоты и параллелизма дорогой проверки и её вынесение из async executor. Это риск доступности, а не утверждение о выполненной атаке.

Источники: [agent config](../deploy/kubernetes/agent/config.yaml), [server config](../deploy/kubernetes/server/resources.yaml), [login](../crates/server/src/user_auth.rs), [Origin middleware](../crates/server/src/web_api.rs).

### 3. Минимальный жизненный цикл доступа

API содержит register/login/me/logout, но не управление участниками, смену/сброс пароля, просмотр и отзыв остальных сессий. Роли owner/member уже есть; это не завершённое управление командой. Для beta с одним оператором допустим документированный безопасный административный recovery; для команды нужны приглашение, отзыв доступа и read-only роль. SSO/MFA можно отложить до целевого enterprise-сценария либо использовать внешний identity perimeter.

### 4. Проверка настоящей цепочки перед публикацией

Обычный `cargo test` пропускает `#[ignore]` PostgreSQL tests. CI отдельно запускает только migrations, notification и policy_api. Например, user_auth, tenant_repository и ingestion имеют ignored tests, не включённые в этот перечень. Frontend Playwright использует `page.route`/`mockApi`; CI не поднимает настоящий backend/DB. Текущие контракты совпадают, однако frontend CI не получает authoritative backend artifact и в основном проверяет свою копию.

Нужен release gate: чистая установка → auth → токен → реальное событие от агента → группа в UI → release diff → внешнее уведомление → обновление/миграция. PostgreSQL suites для доступа, изоляции, ingestion и retention должны исполняться явно. Исторические ручные cluster acceptance полезны, но не заменяют такой gate для выпускаемой версии.

### 5. Достоверность наблюдений и эксплуатационные пределы

Агент имеет ограниченную очередь в памяти и drop counters; replay покрывает pending batches живого процесса, а не переживание его перезапуска. Нельзя обещать безусловно полную историю. Нужны понятные пользователю пробелы наблюдения, поддерживаемый outage window и нагрузочная проверка ingestion + reads + retention вместе. Disk spool необходим, если продукт обещает сохранность при рестарте/долгой недоступности; для диагностической beta допустима честно ограниченная модель потерь.

Имеющиеся тесты на 40,000 identities измеряют последовательные чтения одного приложения, а не устойчивую приёмку потока от многих агентов. Подтверждён также ответ 1,321,222 байта при десяти oversized labels; top-N не гарантирует предел размера ответа. До объявления ресурсных гарантий нужен backend budget полей/ответа и регрессия существующих oversized значений.

Источники: [buffer](../crates/agent/src/delivery.rs), [benchmark и ограничения](data-visualizations-high-cardinality.md), [retention performance](runtime-events-retention.md).

## P1: функции для полезной командной beta

1. Готовый путь уведомления хотя бы в Slack или другой канал пилотной команды: готовый адаптер/шаблон, test delivery, полезный контекст и deep link. Универсальный подписанный webhook уже есть; нативных Slack/PagerDuty адаптеров в просмотренном коде не найдено. В текущем overlay доставка выключена — это вопрос активации существующего механизма, не отсутствующая подсистема.
2. Полный первый сценарий: установить → увидеть ожидаемое поведение → воспроизвести изменение → сравнить релизы → обозначить известное поведение существующими policies/suppressions → получить только полезное новое событие. Нужны демоприложение и короткий walkthrough.
3. Единая проверенная support matrix. Документ обещает Kubernetes 1.32+, containerd 2.x, cgroup v2, kernel 6.1+, x86_64 и Deployment. Acceptance описывает kernel 5.15 и Job; код умеет часть более общих owners. Это несогласованность границ поддержки, а не доказанная полная поддержка всех workloads. ARM64, StatefulSet, Job/CronJob приоритетны по реальным пилотам.
4. Связь расследования с существующими логами/трейсами и удобный экспорт свидетельств. Не обязательно строить собственное хранилище логов и APM.
5. Доступная инструкция backup/restore с фактической проверкой восстановления, sizing, правила обновления и перечень известных ограничений. Встроенная HA PostgreSQL для beta не обязательна; внешний PostgreSQL уже поддерживается.
6. Публичные release notes, security contact, политика поддержки версий и понятное объяснение привилегий агента, включая SYS_ADMIN на reference kernel. Лицензия Apache-2.0 уже есть.

## Преимущества и ограничения

Сильнейшая продуктовая гипотеза — «показываем, как изменилось поведение приложения после релиза, и помогаем разобрать это как очередь задач». Здесь вместе работают grouping, inventory, releases, diff, suppression и triage. Это потенциальное преимущество удобства, пока не доказанное пользовательскими сравнительными тестами.

Дополнительные сильные стороны: self-hosted хранение; ограничение собираемых данных; аккуратное разделение observed/inferred/unknown (например, SIGKILL не приравнивается к OOM); долговечность webhook delivery и retention coverage; готовый UI поверх собственного runtime pipeline.

eBPF, Kubernetes attribution, self-hosting и базовые runtime-события не уникальны. Нет подтверждённого преимущества по CPU/RAM, цене эксплуатации или масштабу. Против широкого APM продукту недостаёт глубины метрик/трейсов/профилирования; против runtime security — prevention/enforcement и готовой большой библиотеки detection rules; против зрелых продуктов — поддерживаемых окружений, интеграций и независимых deployment references. Эти направления не нужно все строить до beta: необходимо выбрать обещание продукта.

См. отдельное [исследование конкурентов и запросов пользователей](competitor-research-2026-09-03.md). Публичные issues дают конкретные примеры боли, но не измеряют её частоту или размер рынка.

## Рекомендуемое решение о выпуске

- Сейчас: пилоты с сопровождением на явно проверенном окружении.
- После P0: ограниченная публичная beta с release notes и известными ограничениями.
- Перед широкой GA: независимые установки, production-shaped нагрузка, доказанное восстановление/обновление, стабильность на выбранной support matrix и несколько команд, регулярно решающих реальную задачу.

Предлагаемый фокус следующего этапа — установка, доступ, реальная release-проверка и первый полезный alert. Новые виды событий, AI-анализ, универсальный APM, собственная HA-БД и enforcement не являются обязательными для такого позиционирования.
