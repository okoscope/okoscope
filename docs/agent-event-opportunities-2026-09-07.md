# Недорогие дополнительные события агента — 2026-09-07

Это исследование вариантов, а не описание реализованных возможностей. «Недорого» ниже — инженерная оценка частоты срабатываний и объёма данных; новые профили не измерялись. Рекомендуемый первый набор: cgroup OOM/лимиты и ошибки exec/bind. Затем — отдельные опасные сигналы, агрегированные TCP retransmit/reset и завершение асинхронного connect.

## Что уже есть

Уже есть process exec/exit, syscall entry, TCP connect/listen/accept, опциональные DNS/file activity. `try_connect_exit` сохраняет errno ошибок и отдельно `EINPROGRESS`; расширение — конечный результат асинхронного подключения. Kubernetes termination/restart/OOMKilled также [поддерживается](process-termination-operator-guide.md); SIGKILL сам по себе не доказывает OOM.

[Имеющийся benchmark](benchmarks/agent-resources-2026-09-07.md) показал около 41m CPU в фоне, 59–64m в burst и 56.5 MiB working set для одного небольшого workload. Но были 729 capacity drops и повторные stream resets; тест не измерял agent-disabled A/B или полные расходы eBPF на стороне приложения. Эти цифры нельзя переносить на новые профили или использовать как доказательство свободной пропускной способности.

## Приоритеты

| Приоритет | Событие и практическая польза | Источник и предполагаемый бюджет | Ограничения |
|---|---|---|---|
| 1 | `process.exec_failed`: отсутствующий бинарник/интерпретатор, запрет запуска, неверный формат | Пары `sys_enter/exit_execve` и `execveat`; ограниченная строка пути на входе, наружу только отрицательный результат. В обычной работе редкий выходной поток | Проверка выполняется и для успешных попыток. PATH-поиск может давать ожидаемые ENOENT; нужна агрегация по workload/path/errno. Относительный путь и execveat через fd нельзя выдавать за канонический executable |
| 1 | `network.bind_failed`: занят порт, запрещён адрес/порт | `sys_enter/exit_bind`; сохранять ограниченный sockaddr, публиковать только ошибки | Listen уже есть. Успешный bind не означает, что сервер слушает. Протокол, namespace, IPv4/IPv6 и UNIX sockets надо разделять |
| 1 | `container.resource_event`: OOM kill, memory.high/max, отказ по pids.max | Чтение дельт cgroup v2 `memory.events.local`, `pids.events`; уведомления об изменении либо ограниченный периодический опрос | Cgroup-счётчик не даёт PID и точное время каждой операции. Не суммировать родительские и дочерние hierarchical counters. Новую cgroup начинать с baseline |
| 1–2 | `process.signal_generated`: SIGKILL, SIGTERM, SIGSEGV, SIGABRT с адресатом | `signal:signal_generate`; ранний фильтр номера сигнала и scope. Обычно небольшой поток при коротком allowlist | Генерация не равна доставке или завершению. SIGCHLD и таймерные сигналы по умолчанию исключить. Текущий task может быть kernel-context, а не пользовательским инициатором |
| 1–2 | `container.pressure`: длительная нехватка CPU/memory/I/O; `container.cpu_throttled` | Редкое чтение pressure/cpu.stat; события о переходе порога с cooldown, а не каждая выборка | Стоимость растёт с числом cgroups. PSI и throttling — разные явления; нужны отдельные поля и пороги |
| 2 | `network.tcp_degraded`: retransmits и resets | `tcp:tcp_retransmit_skb`, `tcp_receive_reset`, `tcp_send_reset`; счётчики в bounded BPF map, периодический агрегат по workload/peer | Во время сетевой аварии поток может стать большим. RST не обязательно ошибка приложения. В timer/softirq нельзя брать `current` как владельца сокета; нужна сохранённая socket attribution |
| 2 | `network.connect_completed`: итог после EINPROGRESS и время handshake | Дополнение существующего `sock:inet_sock_set_state`, состояние по сокету и TTL | Это затраты на каждый отслеживаемый сокет. Переход состояния не всегда даёт точный errno; потерю корреляции надо показывать как unknown |
| 3 | `process.credentials_changed` / результат чувствительного syscall | Узкие syscall entry/exit для setuid/setresuid/setgid/capset; сохранять результат и ограниченный набор аргументов | Успех syscall и фактическое повышение привилегий различаются. Переходы через exec/setuid file не покрываются одним setuid hook; user namespaces осложняют UID=0 |

Retry loops, exec workloads, signal storms и аварии способны сделать любой поток частым.

## Проверенные источники и смысл событий

- **Syscall errors.** Linux предоставляет syscall-specific entry с аргументами и exit с return value; инфраструктура dispatch всё равно работает через syscall entry/exit. Узкий tracepoint ограничивает вызовы нашей BPF-программы, но не делает базовую tracing стоимость нулевой. [Linux v6.12 trace_syscalls.c](https://raw.githubusercontent.com/torvalds/linux/v6.12/kernel/trace/trace_syscalls.c). ENOENT может относиться к интерпретатору; редкие fatal exec failures не возвращаются через syscall exit. [execve(2)](https://man7.org/linux/man-pages/man2/execve.2.html). Bind возвращает, среди прочего, EADDRINUSE/EACCES/EADDRNOTAVAIL. [bind(2)](https://man7.org/linux/man-pages/man2/bind.2.html).
- **Cgroup counters.** `memory.events` иерархический, `memory.events.local` локальный. `high` — throttling/direct reclaim, `max` — попытки превышения лимита, `oom` — OOM condition, `oom_kill` — убитые OOM killer процессы. Это разные сигналы. `pids.events:max` считает отказы из-за лимита процессов; `cpu.stat` содержит `nr_throttled`/`throttled_usec` при включённом CPU controller. Агент может преобразовать дельты в оконные события с границами интервала, дополнив Kubernetes OOMKilled. [cgroup v2](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html?highlight=freezer).
- **OOM по процессу.** `oom:mark_victim` сообщает выбранную жертву; в Linux 6.12 включает PID, comm и показатели памяти. Layout нужно проверять на используемых ядрах 5.15/6.8. Контекст исполняемого OOM killer не равен жертве: cgroup/PID брать у target task, не у current. [oom trace definitions v6.12](https://raw.githubusercontent.com/torvalds/linux/v6.12/include/trace/events/oom.h), [место вызова mark_oom_victim](https://github.com/torvalds/linux/blob/master/mm/oom_kill.c). Userspace OOM killers этим hook не покрываются.
- **Signals.** `signal_generate` содержит номер, code, target PID/comm и result. Документация прямо предупреждает, что сигнал может потеряться, игнорироваться или измениться до `signal_deliver`; сопоставление не гарантировано. Поэтому не подменять им имеющийся process.exit. [signal trace definitions v6.12](https://raw.githubusercontent.com/torvalds/linux/v6.12/include/trace/events/signal.h).
- **PSI.** Есть cpu/memory/io pressure на cgroup v2. Trigger будит poll/epoll при превышении stall-time порога; нужен отдельный FD на trigger. Kernel monitor активен при stall, notifications ограничены одной на окно. Много monitors требуют измерения. [PSI](https://docs.kernel.org/accounting/psi.html).
- **TCP.** Kernel tracepoints дают retransmit/reset и адреса, однако поля различаются между версиями; часть reset событий может не иметь полноценного сокета. [TCP trace definitions v6.12](https://raw.githubusercontent.com/torvalds/linux/v6.12/include/trace/events/tcp.h). `EINPROGRESS` означает незавершённое неблокирующее подключение; конечную ошибку приложение может получить через `SO_ERROR`. [connect(2)](https://man7.org/linux/man-pages/man2/connect.2.html). Корреляцию completion и handshake latency следует вводить отдельным профилем после проверки сокетного lifecycle.
- **Privileges.** Семантика setuid зависит от привилегий; успешный вызов не обязательно означает получение root. [setuid(2)](https://man7.org/linux/man-pages/man2/setuid.2.html). Полное наблюдение credentials требует отдельной реализации, например проверки old/new в `commit_creds`. [Linux cred.c](https://raw.githubusercontent.com/torvalds/linux/v6.12/kernel/cred.c). BPF LSM требует отдельного профиля поддержки. [LSM BPF](https://docs.kernel.org/bpf/prog_lsm.html).

## Условия дешёвого сбора

Текущий DaemonSet монтирует `/sys/fs/cgroup` read-only (`deploy/helm/okoscope-agent/templates/daemonset.yaml`). Поэтому первый cgroup-профиль — периодические read-only дельты: PSI trigger требует открытия с записью и в текущую схему mount не помещается. Это производные события агента поверх kernel counters, а не новые eBPF tracepoints. CgroupResolver уже сопоставляет inode с container ID; для чтения файлов понадобится сохранять пути. Не считать наличие всех полей из latest documentation гарантированным на старых ядрах: каждый файл/ключ требует feature detection.

1. Рано проверять наблюдаемые cgroups, затем фильтр типа/errno и только потом копировать строки, резервировать ring buffer и выполнять userspace enrichment. Для чужого target task/socket фильтр должен опираться на его владельца. В текущих общих emit/connect путях selected-cgroup фильтра перед ring нет; последующая userspace attribution не экономит этот участок.
2. Редкие факты передавать отдельно; частые ошибки/retransmits/pressure — агрегатами с count, first/last timestamp, окном и явными потерями. Ограничивать число ключей, строки, карты, TTL и выходную скорость. Output rate cap не ограничивает число вызовов probe или стоимость уже выполненной работы.
3. Проверять `available_events` и `events/.../format` на каждой поддерживаемой комбинации ядра/архитектуры, объявлять unsupported profile. Ссылка на определение из v6.12 не доказывает совместимость конкретной ноды. [Linux Event Tracing](https://docs.kernel.org/trace/events.html).
4. Перед включением по умолчанию сделать A/B на одинаковом workload: agent off / текущий profile / плюс один новый. Считать приложение p95/p99 и throughput, node CPU, agent CPU/RSS/working set, map/ring/queue drops, delivered bytes/records и рост БД. Отдельно проверять error storm, много cgroups и backend outage. Проценты overhead без такого теста неизвестны.

Полные syscall/firehose, каждый read/write, packet capture, scheduler/page-fault events и стеки на каждую операцию не подходят для первого дешёвого профиля: бюджет привязывается к высокочастотному hot path. Новая реализация и публичная документация возможностей в этом исследовании не менялись.
